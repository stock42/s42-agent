# S42 Agent — Plan v1.0.5

Fecha: 2026-10-03. Estado: **E1–E5 implementadas; integración E6 y CI validadas;
aceptación de mouse físico pendiente**.

Este documento reúne el alcance solicitado y los aportes de diseño para que
cada tarea tenga planificación, seguimiento visual, verificación e historial
de cambios. Es el plan de trabajo solicitado en esta ruta. Su nombre identifica
el objetivo v1.0.5; no cambia la versión actual de `package.json` (0.1.1), no
inicia la implementación ni autoriza una release.

## 1. Resultado esperado

El usuario debe poder pedir una funcionalidad y observar, dentro de la TUI:

1. Qué entendió el agente y qué etapas va a realizar.
2. Qué tareas están pendientes, en progreso y terminadas.
3. Qué archivos cambió y cómo eran antes de la tarea.
4. Qué pruebas planeó, cuáles ejecutó y qué resultados obtuvo.
5. Qué commit corresponde al trabajo y qué quedó pendiente.
6. Cómo continuar una tarea después de cancelar o cerrar el agente.

En proyectos web, el agente también debe poder operar Chrome para ejecutar los
escenarios previstos, observar errores, corregirlos y volver a verificar.

```text
Pedido → inspección y plan → TODO.md / tablero → implementación
                                              ↓
                              pruebas / Chrome / evidencia
                                              ↓
                              diff → CHANGELOG.md → commit
                                              ↓
                                  resultado o bloqueo real
```

El cierre Git depende de las instrucciones del proyecto. Las reglas que se
generen con la acción de AGENTS.md incluirán changelog y commit; el harness no
debe trasladar silenciosamente la política de este repositorio a otros proyectos.

## 4. Contratos que se conservan

- TypeScript estricto, Bun y entrypoint único `index.ts`; núcleo sin nuevas
  dependencias de runtime. Git y Chrome son programas externos.
- QBasic como apariencia predeterminada, paletas semánticas existentes e UI
  ES/EN mediante `src/ui/i18n.ts`.
- Prompt siempre visible. Editor central de solo lectura, con selección,
  Unicode y scroll; los formularios de tarjetas son controles auxiliares.
- Mouse y teclado; no asignar acciones a F1–F12. Conservar Escape, Ctrl+N,
  Enter, Shift+Enter y Ctrl+J según los contratos actuales.
- Projects sigue solicitando solamente Name y Folder.
- Sesión, tareas, cwd de tools y cancelación pertenecen al proyecto de origen,
  aunque el usuario cambie de pestaña durante la ejecución.
- Sin cuotas propias de tokens, etapas, duración, tamaño o resultados.
  Conservar compactación, historial original y cancelación explícita.
- No consultar la red ni iniciar servidores o navegadores al arrancar.
  Abrir el panel Git tampoco inicia fetch, pull o push.
- Mantener el backend JSON/JSONL explícito y la compatibilidad de sesiones
  anteriores. No crear `.env.local` ni otro mecanismo de configuración.
- Validar iteraciones desde `bun run dev`; builds, benchmarks y smoke de
  distribución quedan para una entrega de binarios solicitada.

## 5. Panel Git e historial

### 5.1. Vistas

Un panel `Git` por proyecto, accesible desde `Vista → Git`, con cuatro vistas:

| Vista | Información y acciones de consulta |
| --- | --- |
| Cambios | Archivos nuevos, modificados, eliminados, renombrados, staged y conflictos; diff de archivo e índice. |
| Historial | SHA, mensaje, autor, fecha, referencias y detalle de archivos/diff de cada commit. |
| Branches | Rama actual, ramas locales y remotas conocidas, upstream y ahead/behind cuando se puedan calcular. |
| CHANGELOG | Lectura del archivo del proyecto; estado explícito cuando no existe. |

Mostrar también la raíz real del repositorio cuando difiera de la carpeta del
proyecto. Las referencias remotas representan la información local disponible;
no equivalen a una consulta reciente al servidor.

Git conservará la autoridad sobre commits y ramas. El panel consultará esos
datos mediante comandos internos con argv escapado y salida sin colores.
Utilizar formatos estables para máquinas, como `status --porcelain=v2 -z`, y
respetar nombres con espacios, Unicode, tabulaciones o saltos de línea.
El contrato de porcelain y separación NUL está documentado en
[git-status](https://git-scm.com/docs/git-status).

El historial se cargará progresivamente al navegar, sin un máximo artificial
de commits. Un binario se identificará como tal; no se inventará un diff textual.
Refrescar al abrir, por acción del usuario y después de operaciones que puedan
cambiar el repositorio. Descartar respuestas de consultas pertenecientes a una
pestaña o carpeta anterior.

La primera entrega cubre consulta y revisión. Crear/cambiar/eliminar ramas,
merge, rebase, reset y publicación remota desde botones quedan fuera de este
plan; no son necesarios para el historial solicitado.

### 5.2. Historial por tarea

Al comenzar una tarea de modificación, registrar HEAD, rama, estado del índice
y cambios preexistentes relevantes. Conservar versiones anteriores de los
archivos que el agente vaya a editar mediante tools nativas.

La ficha de tarea debe distinguir:

- Estado del repositorio antes de comenzar.
- Cambios observados durante el trabajo.
- Ediciones atribuibles a las herramientas registradas.
- Commit o commits asociados, una vez confirmados por Git.

Un diff entre dos momentos no demuestra por sí solo autoría: shell, programas
externos u otra instancia pueden modificar los mismos archivos. En ese caso,
mostrar cambios observados y atribución desconocida, sin adjudicarlos al agente.
No implementar copias completas del repositorio ni un sistema de undo general.

### 5.3. Casos de aceptación

- Repositorio limpio, sucio, sin commits y con HEAD separado.
- Proyecto dentro de un repositorio superior y worktree con `.git` como archivo.
- Renombres, eliminaciones, binarios, conflictos y archivos staged previamente.
- Sin upstream, referencias remotas desactualizadas y Git no instalado.
- Scroll y selección del diff; cambio de proyecto durante una consulta.
- Dos tareas sobre una misma carpeta no presentan cambios ajenos como propios.

## 6. Planificación, ejecución y cierre

### 6.1. Instrucciones del agente

El system prompt debe exigir para toda tarea de ejecución:

1. Leer el pedido, las instrucciones aplicables y los archivos relevantes.
2. Expresar el objetivo y el resultado observable esperado.
3. Registrar un plan breve con etapas, dependencias y criterios de aceptación.
4. Definir la verificación antes de implementar: comando, escenario o revisión
   proporcional al cambio. Una edición documental puede requerir solo revisión.
5. Trabajar por etapas y actualizar estado conforme ocurren los resultados.
6. Ante un fallo, registrar el error, corregir la causa y repetir la prueba
   pertinente; conservar el resultado fallido anterior.
7. Revisar el diff y cumplir el cierre documental/Git del proyecto.
8. Informar cambios, validación, commit y pendientes con sus evidencias.

Una consulta informativa no necesita crear archivos ni tarjetas. Un pedido de
planificación termina al entregar el plan solicitado; no dispara implementación.
Una corrección mínima puede tener una sola tarea con su comprobación. Planificar
no introduce una aprobación obligatoria adicional cuando el trabajo ya está
autorizado. El plan visible resume acciones y criterios; no sustituye ni inventa
reasoning del proveedor.

### 6.2. Herramientas y control del loop

Agregar herramientas nativas pequeñas, con nombres propuestos:

| Tool | Responsabilidad |
| --- | --- |
| `task_plan` | Crear o revisar las etapas de un pedido, sus criterios y verificaciones previstas; devolver IDs estables. |
| `task_update` | Actualizar progreso, bloqueo, resumen y referencias a resultados existentes. |
| `task_verify` | Ejecutar una comprobación de comando mediante el runner compartido y registrar su resultado real. |

Los cambios de tablero usarán la misma lógica que estas tools. No guardar un
plan libre en el chat y otro plan independiente en la UI. Extender el contexto
de tools con acceso explícito a la tarea del turno, manteniendo compatibles los
consumidores actuales de `src/agent/tools.ts`. Validar los campos estructurados
que requieran estos contratos, sin crear un framework de schemas.

El harness debe exigir un plan registrado antes de las mutaciones de ejecución
y comprobar el cierre antes de reportar éxito. El plan inicial puede incluir
una etapa de inspección y refinarse después. Para shell arbitrario, exigir ese
plan inicial en tareas de ejecución: no intentar deducir con heurísticas si un
programa completo es de solo lectura. Las consultas internas conocidas de Git
y las herramientas de lectura no necesitan una tarjeta por cada llamada.

Antes de aceptar una finalización, verificar tareas pendientes, criterios,
pruebas requeridas y cierre Git aplicable. Si falta trabajo ejecutable, devolver
al modelo la lista concreta de pendientes. Si hay un bloqueo real o el usuario
cancela, terminar el turno con ese estado y conservar la tarea abierta.

Separar **turno finalizado** de **tarea completada**: hoy el evento de turno
`completed` no certifica pruebas ni aceptación funcional. Mantener recuperación
por `finish_reason: length` y compactación sin perder los IDs del trabajo activo.
Un modelo sin tools conserva el modo de orientación y no marca trabajo como
ejecutado. Ninguna comprobación estructural garantiza por sí sola corrección
semántica; esa evidencia proviene de los tests y escenarios observados.

## 7. TODO.md y tablero Kanban

### 7.1. Fuente de verdad

`TODO.md`, en la raíz del proyecto registrado, será la fuente de verdad del
contenido, orden y estado de las tareas. SQLite conserva eventos, relación con
sesiones, resultados detallados y preferencias visuales; no mantiene una segunda
versión autoritativa del tablero. El backend legacy conserva los mismos eventos.

Formato propuesto, legible y editable sin S42 Agent:

```markdown
# TODO

## Pendientes

### [T-<uuid>] Agregar historial Git
Pedido: R-<uuid>
Depende de: ninguna
Descripción: consultar los commits del proyecto.
Criterio: abrir un commit permite ver sus archivos y diff.
Verificación prevista: prueba con repositorio temporal y revisión TUI.
Resultado: pendiente.

## En progreso

## Terminadas
```

Los identificadores reales serán UUID, independientes del título y del idioma.
Los nombres de las secciones del archivo son parte de su formato; cambiar el
idioma de la UI no reescribe contenido del usuario. Guardar en cada tarjeta el
resumen de verificación y las referencias disponibles, además de dependencias,
motivo de bloqueo y criterio de aceptación.

Si existe un TODO.md con otro formato, leerlo y ofrecer adaptación con preview.
Preservar texto ajeno a las tarjetas reconocidas. Si contiene una tarjeta
malformada, mostrar el problema sin descartarla ni reescribir todo el documento.

### 7.2. Sincronización

- Leer la versión actual antes de cada escritura y guardar mediante reemplazo
  atómico. Comparar la revisión leída para detectar ediciones concurrentes.
- Si el archivo cambió externamente, recargar y reaplicar solo cambios que no
  colisionen. En una colisión sobre la misma tarjeta, mostrar ambas versiones.
- Coordinar escrituras por ruta canónica, también cuando dos proyectos apuntan
  a la misma carpeta. El control entre procesos debe impedir perder cambios.
- Registrar primero la intención en el historial, luego el cambio de archivo y
  por último su confirmación. Ante un cierre intermedio, reconciliar contra el
  archivo actual; no asumir una transacción atómica entre SQLite y filesystem.
- Refrescar al volver al panel y ante cambios detectados en el archivo. Liberar
  listeners y recursos al cerrar o cambiar la carpeta del proyecto.
- Abrir el tablero vacío no crea TODO.md por sí solo. Se crea al registrar la
  primera tarea o cuando el usuario lo solicita.

### 7.3. Interacción

Tres columnas: **Pendientes**, **En progreso** y **Terminadas**. Una tarea
bloqueada permanece en progreso con su motivo. Una cancelación no borra trabajo
ni convierte automáticamente la tarjeta en terminada.

```text
┌──────────────────── Proyecto ─────────────────────────┐
│ Respuestas  Archivos  Git  Tareas  Verificación        │
│ ┌─ Pendientes ─┐ ┌─ En progreso ─┐ ┌─ Terminadas ──┐ │
│ │ Chrome      │ │ Panel Git     │ │ Detectar Git  │ │
│ │ AGENTS.md   │ │ Pruebas: 2/3  │ │ Revisado      │ │
│ └─────────────┘ └───────────────┘ └───────────────┘ │
└──────────────────────────────────────────────────────┘
┌──────────────────── Prompt ──────────────────────────┐
│ Escribí tu pedido…                                    │
└──────────────────────────────────────────────────────┘
```

Es un boceto de distribución, no una captura de implementación. Crear, editar,
reordenar, mover y abrir tarjetas mediante mouse y teclado; arrastre entre
columnas con feedback de destino. En ancho reducido, una columna seleccionable
a la vez, conservando acceso a todas las tareas y al prompt.

El agente solo puede marcar una tarea terminada si cumple su aceptación y sus
verificaciones requeridas. Si el usuario la mueve manualmente, registrar ese
origen sin fabricar pruebas. Mostrar por separado el estado de ejecución, la
validación y el cierre Git; mover una tarjeta no ejecuta un commit.

## 8. Ficha de verificación y recuperación

Cada tarea tendrá una ficha accesible desde su tarjeta y desde
`Vista → Verificación`, con los siguientes datos:

| Dato | Contenido |
| --- | --- |
| Verificación prevista | Qué debe comprobarse y por qué. |
| Estado | Pendiente, ejecutando, aprobada, fallida, bloqueada o no aplicable con motivo. |
| Ejecución | Comando o escenario, cwd/URL, inicio, fin y cancelación. |
| Resultado | Exit code, salida o aserciones observadas; referencia al evento original. |
| Evidencia | Archivos, capturas o resultados de herramientas realmente disponibles. |
| Vigencia | Revisión de código o estado de archivos al que corresponde la prueba. |
| Origen | Ejecución del harness, observación de navegador o confirmación manual del usuario. |

Un comando solo termina cuando el proceso finaliza. Un texto «OK» con proceso
vivo no aprueba la verificación. Exit code cero se presenta como resultado del
comando; no demuestra automáticamente que se cumplieron todos los criterios.
Un build correcto no acredita interacción web, despliegue ni otro sistema operativo.

Si cambia código relevante después de una prueba, marcar la evidencia anterior
como pendiente de revalidación. Una omisión con motivo no equivale a una prueba
aprobada. Las confirmaciones manuales quedan atribuidas a quien las realizó;
el modelo no puede simular una aprobación humana.

Al reabrir, reconstruir tablero desde TODO.md y cargar eventos asociados. Una
verificación interrumpida queda identificada como tal. La acción «Continuar
tarea» recupera el objetivo, última etapa y evidencia, comprueba el estado real
y sigue desde lo pendiente. No reejecuta automáticamente herramientas con
posibles efectos anteriores ni inicia trabajos al arrancar el programa.

## 9. Tools → Autogenerar AGENTS.md

### 9.1. Flujo

1. Seleccionar la acción dentro del proyecto activo.
2. Inspeccionar README, manifests, scripts, estructura y AGENTS aplicables.
3. Usar el modelo configurado para redactar un borrador con los hechos observados.
4. Mostrar preview y, si ya existe el archivo, diff de la actualización.
5. Guardar al elegir «Aplicar»; cancelar conserva el archivo anterior.

La generación usa el contexto del proyecto capturado al iniciar, aunque se
cambie de pestaña. Si no hay modelo utilizable o la generación falla, mostrar el
error conservando cualquier borrador recibido. Analizar scripts no implica
ejecutarlos. No inventar comandos de test, políticas o capacidades del proyecto.

### 9.2. Contenido requerido

- Descripción breve del proyecto y su stack comprobado.
- Carpetas y puntos de entrada relevantes.
- Comandos reales de desarrollo y validación disponibles.
- Convenciones e instrucciones existentes que deben conservarse.
- Planificación por etapas y verificación proporcional a cada tarea.
- Las dos reglas solicitadas, expresadas literalmente:

> Siempre mantener actualizado CHANGELOG.md luego de cada tarea.
>
> Siempre hacer commit al terminar la tarea.

A continuación, precisar su aplicación: registrar cambios efectivamente
realizados, validar y revisar el diff, incluir CHANGELOG en el mismo commit y
agregar solo el trabajo de la tarea. Una consulta sin cambios no genera entrada
ni commit vacío. No marcar el cierre completo si el commit falla.

Conservar reglas existentes de pull/push y rama. No añadir push a un proyecto
que no lo pida ni reemplazar sus instrucciones por las de S42 Agent. Cuando
una regla nueva contradiga una existente, destacar el conflicto en el preview.

La generación debe ser repetible sin duplicar secciones. Respetar AGENTS
anidados; generar el archivo de la raíz del proyecto no elimina su alcance.

## 10. Detección e inicialización Git

Consultar a Git si la carpeta pertenece a un árbol de trabajo y resolver su
raíz. No depender de encontrar un directorio `.git` dentro del proyecto:
subcarpetas y worktrees requieren la detección real documentada en
[git-rev-parse](https://git-scm.com/docs/git-rev-parse).

Cuando no haya repositorio, ofrecer **«Inicializar repositorio Git»** y
**«Continuar sin Git»**. La acción muestra la carpeta de destino y ejecuta init
solo cuando el usuario la elige. Recordar el descarte durante la sesión para
no interrumpir repetidamente; mantener la acción accesible desde el panel.

Después, comprobar que Git reconoce el repositorio y actualizar la UI.
Inicializar no crea automáticamente un remoto, un repositorio en GitHub ni un
commit de todos los archivos. Si Git no está disponible, informar ese estado;
no confundirlo con una carpeta sin repositorio ni instalar software por inferencia.

## 11. Cierre de tarea: CHANGELOG y commit

Orden del flujo cuando las instrucciones del proyecto exijan ese cierre:

1. Completar implementación y verificaciones pertinentes.
2. Revisar cambios frente al estado inicial y resolver atribución ambigua.
3. Actualizar TODO.md y CHANGELOG.md con el resultado real.
4. Preparar exclusivamente los cambios de la tarea, preservando el índice y
   los archivos preexistentes ajenos. Si hay cambios mezclados en el mismo
   archivo, separar los hunks o presentar el bloqueo concreto.
5. Crear el commit conforme a la política del proyecto y verificarlo con Git.
6. Registrar SHA, resultado y relación con la tarea en el historial de sesión.
7. Hacer push únicamente cuando el proyecto o el usuario lo hayan autorizado;
   distinguir commit local, push fallido y publicación confirmada.

La tarjeta puede tener el trabajo validado y el cierre Git pendiente o fallido.
El estado de cierre aparece junto al estado de ejecución. Guardar el SHA recién
creado en los eventos evita modificar TODO.md después de cada commit solo para
insertar el hash de ese mismo commit. Una exportación posterior puede incluirlo.

Sin repositorio, el cierre informa «Git no disponible» y mantiene la acción de
inicialización; no inventa un commit ni impide usar el agente para otros trabajos.
Si se interrumpe después de crear un commit, inspeccionar Git antes de reintentar
para no duplicarlo. Errores de hooks, conflictos o falta de configuración deben
quedar visibles y no disparar force, reset o descarte de cambios.

## 12. Chrome para pruebas reales

### 12.1. Integración propuesta

La primera opción a validar es Chrome DevTools MCP como integración externa
opcional sobre el cliente MCP existente. Ofrece navegación, interacción,
capturas, consola y red. Su instalación oficial requiere Node.js y Chrome;
ese runtime pertenece al servidor externo y no se incorpora al núcleo Bun.
No afirmar que ejecutarlo con Bun es compatible sin una prueba.
[Proyecto oficial](https://github.com/ChromeDevTools/chrome-devtools-mcp).

Playwright MCP queda como alternativa para evaluar si la prueba de integración
detecta una carencia concreta; ofrece interacción mediante snapshots de
accesibilidad, útil para modelos sin visión. No integrar dos motores en esta
entrega. [Proyecto oficial](https://github.com/microsoft/playwright-mcp).

Si se exige que también el servidor de navegador funcione únicamente con Bun,
resolver esa compatibilidad antes de implementar la fase. Un cliente CDP propio
sería otro alcance, no un reemplazo automático de la integración propuesta.

### 12.2. Experiencia de uso

`Tools → Chrome / pruebas web` permite configurar o seleccionar la conexión,
abrir una sesión de pruebas y consultar su estado. Reutilizar el registro MCP;
no duplicar configuración ni instalar automáticamente herramientas externas.

Usar un perfil de pruebas separado como opción inicial. Conectarse a un Chrome
existente es una selección explícita. Mostrar proyecto propietario, URL/pestaña
activa, conexión, actividad en curso y errores. La selección de una pestaña de
Chrome no cambia el cwd de las herramientas del proyecto.

El navegador se abre cuando se solicita una prueba web o se elige la acción.
Mantener WebServer con su ciclo de vida actual; probar una aplicación puede
usar una URL ya disponible o su comando de desarrollo autorizado. No convertir
WebServer en una herramienta LLM ni iniciarlo al abrir el agente.

### 12.3. Capacidades y evidencia

- Navegar, inspeccionar estructura y esperar condiciones observables.
- Hacer clic, escribir, completar formularios y manejar diálogos.
- Probar el flujo principal y errores relevantes al cambio.
- Verificar distintos tamaños cuando se modifica una interfaz responsive.
- Recoger errores de consola y requests relevantes, junto con su resultado.
- Guardar capturas cuando aporten evidencia y asociarlas a la verificación.
- Corregir y repetir el escenario que falló, conservando ambos resultados.
- Cuando sea útil para regresión, guardar un test reproducible con el framework
  existente del proyecto; no instalar uno nuevo solo por ejecutar una prueba.

La evidencia debe incluir URL, pasos, resultado esperado, resultado observado y
fuente de observación. Un snapshot o una captura por sí solos no aprueban un
flujo. Un modelo sin visión puede operar con estructura/texto y conservar
imágenes para revisión humana; no afirmar que analizó píxeles.

### 12.4. Adaptaciones técnicas necesarias

1. Preservar contenido de imagen y referencias de archivos MCP, además del texto.
2. Adaptar mensajes/sesiones/cliente LLM para entregar imágenes solo por formatos
   admitidos por el proveedor. Conservar el vínculo entre call, resultado y archivo.
3. No mostrar base64 como texto en la TUI; mostrar tipo, ruta y acción de apertura.
4. Definir propiedad y duración de la sesión de navegador: hoy el loop cierra
   sus conexiones MCP al terminar cada turno. Retener solo la conexión de
   navegador necesaria por proyecto y cerrarla al desconectar/cerrar/cambiar
   carpeta; no alterar innecesariamente otros servidores MCP.
5. Distinguir recursos iniciados por S42 de un navegador externo ya abierto;
   desconectar este último no debe cerrar ventanas del usuario.
6. Cancelar la operación conserva evidencia parcial y detiene llamadas nuevas.
   Una pestaña cerrada o un servidor caído deja una prueba fallida/interrumpida
   con el error real, sin éxito supuesto.
7. Mantener accesibles los artefactos al reabrir una tarea y reportar archivos
   ausentes explícitamente. No depender de `private/` para runtime o tests.
